# 记忆提取管线诊断：为什么 80 条/16 重叠会导致"张冠李戴"与"找不到主语"

> 相关代码：`backend/mem.go`
> - `memExtractChunkSize = 80`（每批送给 LLM 的消息条数）
> - `memExtractStride = 64`（步进，重叠 16 条衔接上下文）
> - `extractFactsFromChunk()`：单批消息 → LLM → 事实列表

---

## 根本原因：固定条数分段是"盲切"

固定每 80 条切一刀，完全不考虑话题边界、信息密度和主语引入点。这会系统性地产生两类故障。

---

## 一、为什么"张冠李戴"（幻觉）

### 故障链：指代消解的跨段断裂

群聊里"他"、"她"、"那个事"的指代对象经常在 **很早之前** 被引入，比如：

```
第 10 条：张三说他明天来
...（中间 60 条其他讨论）...
第 75 条：他到了吗？
```

当窗口切在 80，第 75 条的"他"指向谁？模型看不到第 10 条（张三），只能基于本段窗口内的信息去猜。如果本段恰好提到了李四，模型就可能把"他"错误地关联到李四身上 —— 这就是张冠李戴。

**16 条重叠救不了这个问题**，因为指代的引入点（第 10 条）远在重叠窗口之外。

### 更隐蔽的故障：重叠区信号噪声比太低

16 条重叠消息在群聊里可能就是几个表情 + 几句"哈哈哈" + "收到"。模型从这 16 条里提取不到任何有效上下文，等于 **零上下文衔接**。这时模型要么硬猜（→ 幻觉），要么承认不知道。

---

## 二、为什么"找不到主语"

### 群聊消息大量省略主语

群聊天然是省略主语的对话体：

```
"那后来呢"
"应该没问题吧"
"多少钱"
"谁说的"
```

这些消息本身没有主语，必须靠上下文推断。问题在于：

- 主语往往在 **几条甚至几十条之前** 被引入
- 如果分段边界恰好切在"主语引入点"和"后续省略主语的讨论"之间，模型就彻底丢失了主语

### 具体场景

```
第 78 条：王五那个项目怎么回事？
第 79 条：听说卡在审批了
第 80 条： ← 分段边界
第 81 条：那后来推进了吗？
第 82 条：好像还是没动
```

窗口 81-160 这段，"那后来推进了吗"的主语是"王五的项目"，但这个主语在第 78 条被引入，恰好在上一段的末尾。16 条重叠覆盖 65-80，如果模型没有主动去提取重叠区的主语信息，就会丢失。

**这就是为什么重叠必须是"结构化摘要"而不是"原始消息"** —— 原始重叠区里的信息，模型不一定会主动去读。

---

## 三、当前方案的三个设计缺陷

| 缺陷 | 后果 |
|------|------|
| **固定条数盲切**，切断话题和主语链 | 找不到主语、话题残缺 |
| **16 条原始消息重叠**，信号噪声比低 | 上下文衔接断裂 |
| **无摘要链传递**，每段独立分析 | 指代消解失败 → 张冠李戴 |

---

## 四、修复方向

核心思路：**不要传递原始重叠消息，而是传递结构化的上下文摘要**。

```
段1分析 → 输出上下文摘要（人物表 + 当前话题 + 未消解指代）
                ↓ 传入
段2分析 → 参考前文摘要消解指代 → 输出更新后的上下文摘要
                ↓ 传入
段3分析 → ...
```

具体来说：

1. **把 16 条原始重叠换成"上一段的结构化摘要"** —— 显式告诉模型"前文提到了谁、在讨论什么"
2. **在 prompt 里强制约束**："无法确定的指代，标注【不确定】，不要猜测"
3. **维护全局实体表** —— 每段分析时参考实体表消解"他/她"，而不是只靠窗口内的信息
